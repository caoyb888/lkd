
这份需求文档描述的是一个相对标准的、典型的“案卷-文件”两级传统档案管理系统。为了契合你提出的“尽量简单化”的原则，技术方案将避免过度设计（如微服务架构、复杂的中间件等），采用目前主流且轻量稳定的 **Java 单体架构（Monolithic Architecture）**。

以下是为你量身定制的详细技术方案：

# 莱矿-档案管理系统技术方案

## 1. 总体架构设计

为了降低开发与运维成本，系统采用**前后端分离**的单体MVC架构。

### 1.1 技术栈选型

- **后端开发框架**：Spring Boot 3.x (或 2.7.x，视团队熟悉度度而定)，提供 RESTful API。
    
- **持久层框架**：MyBatis-Plus（极大简化 CRUD 操作，自带分页及条件构造器）。
    
- **权限安全框架**：Spring Security + JWT / Sa-Token（推荐 **Sa-Token**，极其轻量且对单体系统非常友好）。
    
- **数据库**：MySQL 8.0。
    
- **前端框架**：Vue 3 + Element Plus (组件库现成提供下拉框、表格、表单，极易适配档案录入与列表展示)。
    
- **文件处理**：Apache POI / EasyExcel（用于 Excel 导入导出），Apache POI / docx4j（用于 Word 模板打印）。
    

## 2. 核心业务流程与功能设计

结合需求说明，我们将系统划分为以下几个核心模块，并给出精简的实现思路。

### 2.1 用户与权限模块 (3.1 - 3.3)

- **三级角色划分**：系统配置三种角色：
    
    1. **用户（普通员工）**：新建/补录档案（未提交前可见）、查看/检索档案、申请借阅、查看本部门历史。
        
    2. **档案管理员**：处理借阅申请、审批确认归档、有限修改目录、批量导入。
        
    3. **公司领导**：审批档案的“删除/恢复/销毁”高级操作。
        
- **密码规则校验**：在后端 `UserService` 统一拦截，使用正则表达式进行校验：
    
    代码段
    
    ```
    ^(?=.*[A-Za-z])(?=.*\d)(?=.*[$@$!%*#?&])[A-Za-z\d$@$!%*#?&]{6,}$
    ```
    

### 2.2 数据字典与录入效率 (3.4)

- **数据字典表 (`sys_dict`)**：设计一张通用的字典表。
    
- **业务应用**：在“新建档案”页面加载时，前端一次性请求全宗号、密级、保管期限、分类名称等字典数据，缓存于前端，录入时直接以下拉列表框（Select）展示。
    

### 2.3 档案状态流转与生命周期 (3.5, 3.9 - 3.11)

档案在系统中需要有一个状态字段（建议在表里增加 `status` 字段，或通过审核流程判断），生命周期如下：

1. **草稿状态 (Status: 0)**：立卷人新建，仅自己可见，可改可删。
    
2. **待审核 (Status: 1)**：提交审核后，立卷人不可见（或只读），检查人/审核人可见。
    
3. **待确认 (Status: 2)**：审核人通过，流转到档案管理员界面。管理员可退回给新建人，也可确认。
    
4. **已正式归档 (Status: 3)**：确认后进入正式库，全员可查。
    
5. **销毁/删除状态**：通过 `destroy_flag` 或逻辑删除字段控制。
    

### 2.4 借阅管理 (3.6 - 3.8)

- **借阅单表 (`archive_borrow_record`)**：记录申请人、档案ID、申请数量、借阅天数、审批状态、归档/还回状态等。
    
- **到期提醒**：在“已借阅列表”中，后端计算 `当前时间 - (借阅时间 + 剩余时间)`。为实现简单化，**不引入复杂的定时任务中间件**，直接利用 Spring 自带的 `@Scheduled` 注解，每天凌晨扫描一次该表，发现即将到期或超期的，更新状态或发送系统内通知。
    

### 2.5 打印功能 (3.12)

- **实现方案**：在后端准备好格式规范的 `.docx` 模板文件，利用占位符（如 `{{volume_title}}`）。
    
- **流程**：当用户点击打印时，后端查询 `archive_volume` 和 `archive_file` 的数据，使用组件（如 `poi-tl`，基于 Apache POI 的优秀开源模板引擎）将数据渲染进 Word 模板，并以二进制文件流的形式返回给前端，前端直接下载即可通过本地 Word 打印。

## 4. 关键技术难点与精简解决方案

### 4.1 模糊查询与性能

- **现状**：档案主目录和子目录字段非常多，且支持年度、类目等条件及模糊查询。
    
- **简单化方案**：在前端提供“高级搜索（按年度、分类、档号精准筛选）”和“全局模糊搜索（只针对题名、标题、主题词）”。
    
- **SQL优化**：对高频查询条件字段如 `year`, `category_l1`, `volume_no`, `archive_no` 务必建立**联合索引**或**单列索引**（需求文档中已预留“索引”标识，设计得很好）。避免使用 `LIKE '%xxx%'` 导致全表扫描，如果数据量在十万级以下，MySQL 索引配合合理的条件筛选完全能够支撑，无需引入 Elasticsearch 等重型组件。
    

### 4.2 文件导入（批量导入）

- **现状**：需求提及“因数据较多，数据格式难以核定，导入易出错，不建议批量导入”。
    
- **折中简单方案**：如果管理员确实需要批量导入，提供一个**极简且严格的 Excel 模板**。
    
    - 使用 **EasyExcel** 读取，配置简单的校验注解（如非空、长度限制）。
        
    - **错误处理机制**：导入时，如果某一行出错，直接全单回滚，并定位出“第X行第Y列格式错误”，让管理员修改后重新上传，不进行复杂的“部分成功、部分失败”逻辑处理。
        

### 4.3 档号的自动生成

- **逻辑**：根据需求，档号规则为 `全宗号.一级类目.二级类目.三级类目.设备代号.案卷号`。
    
- **方案**：在用户录入并选择完上述前置下拉框后，前端发送异步请求，后端去数据库中查询当前组合下的最大 `volume_no`（案卷号），将其自增 +1（例如 `002` 变成 `003`），拼接后返回给前端预览。确保在“确认归档”时，后端再次校验唯一性索引。
    

## 5. 项目交付与部署架构

既然追求“尽量简单化”，部署也将采用最原始且高弹性的**单机部署**：

```
                    +-----------------------+
                    |      用户浏览器       |
                    +-----------+-----------+
                                |  HTTP / HTTPS (Port 80/443)
                                v
                    +-----------------------+
                    |      Nginx 反向代理   | (动静分离：静态页面直接返回，
                    +-----------+-----------+  API 请求转发至后端)
                                |
                                v
                    +-----------------------+
                    |  Jar 包 (Spring Boot) | (内置 Tomcat 运行环境)
                    +-----------+-----------+
                                |
                                v
                    +-----------------------+
                    |       MySQL 8.0       | (数据落地存储)
                    +-----------------------+
```

- **打包形式**：前端打包为静态资源，放入 Nginx 托管；后端编译为单个 `jar` 包，直接通过 `nohup java -jar xxx.jar &` 运行。
    
- **备份方案**：写一个简单的 Linux Shell 脚本，利用 `mysqldump` 每天凌晨自动备份数据库，并保留最近 30 天的备份文件至异地或独立磁盘。
